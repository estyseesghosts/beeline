## Retention class

Each row falls into one class:

* Bounded: emoji URL mappings, thread continuations, HTTP clients, capabilities, app registrations, notification records (500), profile cursors (64 per tab), push parser caps, delivery claim lease (2 minutes).
* Expiring: emoji mapping freshness (7 days), thread idle timeout (10 minutes), capability freshness (5 minutes), registration idle expiry (24 hours), delivery claim expiry, periodic work interval (30 minutes).
* Active-scoped: repository states and health, orchestrator states, jobs, poll jobs, stream jobs, write locks, draft and direct authorities, source registry entries, media transition sources, pager jobs and pages, WorkManager chains, registration operation lock. Release follows account removal, replacement, cancel, or close.
* Correctness-lifetime: notification dismissed tombstones, checkpoints, delivery records, repository retired generations, orchestrator removal epochs and account locks, emoji catalog snapshot, emoji active leases. ## Removal and session-replacement order

Account removal runs in this order:

1. The orchestrator calls `unregister`: it clears the generation, cancels jobs, removes the source, invalidates the repository generation, bumps the removal epoch, and marks display inactive.
2. The repository calls `remove`: it bumps the generation, advances the retired tombstone with `maxOf`, retires the write record, deletes durable rows in one transaction, drops memory state, and releases the lock entry when quiescent.
3. The scheduler calls `cancel(accountId)`: it cancels all five unique work names.
4. The source registry drops the entry; the stream controller stops the socket; the presenter path routes nothing because the repository reports retired.

Session replacement runs in this order: capabilities invalidate for the session revision; authorities revoke the old generation and issue a strictly newer one; the orchestrator publishes only when the map, the epoch, and the repository agree; a stale token deactivates only its own entry and never clears the winner. A concurrent removal wins through invalidate-before-delete, the tombstone, the epoch check, stale undo, and the post-removal drop.

## State kinds

* Active entries live in maps keyed by account and die on removal: repository states, orchestrator states, jobs, write locks, authorities, source entries.
* Allocators live for the controller or process lifetime and never reset: orchestrator generation and epoch counters, NoOp generation counter, draft and direct generation counters.
* Tombstones survive removal and use `maxOf`: repository retired generations, orchestrator removal epochs.
* Delivery records live for the retry lifetime: claim expiry bounds posting claims; dismissal and removal release completed records.
* Display state lives for the observation lifetime: orchestrator flows and Android tray output; both clear on removal.
* Foreground state lives for the foreground lifetime: stream controller jobs; `stop` and `close` cancel them.
* WorkManager state lives outside the process: unique work names per account; cancel on removal is the release.
* Revisions fence durable state: session revisions gate capability reuse and push registration recovery; generation zero is the restart-safe callback token and loses to the next sync generation.
* Opaque tokens never parse or compare: thread continuations, sync tokens, profile cursors, stable file names. Admission checks bind each token to its account, query, or session key.
* Borrowed clients carry no account state: HTTP pool entries hold transport reuse only; LRU eviction bounds them.
* Leases keep shared bytes alive: emoji asset leases guard files during reads; delivery claims guard one presentation attempt for two minutes.
